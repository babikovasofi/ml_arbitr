# arbitr_runtime v0.3 — залить в хранилище

**Сначала прочитайте раздел «Важно» ниже: возможно, заливать вообще ничего не нужно.**

Веса в v0.3 байт в байт совпадают с v0.2 — суммы и размеры в `runtime_v0.3/manifest.json`.
Если в бакете уже лежат файлы с такими же суммами, работа сводится к нулю.

Полный каталог с весами (1.8 ГБ) в этот репозиторий не кладётся: GitHub не принимает файлы
больше 100 МБ. Он собирается командой из `arbitrator_ml`:

```bash
uv run python local_model/scripts/build_handoff.py --layout runtime --version v0.3 \
    --base-url https://storage.yandexcloud.net/arbitratorbucket1/arbitr/models/v0.3/
```

## Что заливать

Два файла весов, **плоско**, в бакет бэкенда:

```bash
aws s3 --endpoint-url https://storage.yandexcloud.net \
    cp arbitr_runtime_v0.3/qwen3.5-2b/qwen3.5-2b-q4_k_m.gguf s3://<бакет>/models/
aws s3 --endpoint-url https://storage.yandexcloud.net \
    cp arbitr_runtime_v0.3/qwen3.5-0.8b/qwen3.5-0.8b-q4_k_m.gguf s3://<бакет>/models/
```

`<бакет>` — тот, что задан бэкенду переменной `S3_BUCKET`. Ключ обязан быть
`models/<имя файла>` без вложенных папок: приложение просит файл по имени через
`GET /download/{имя}`, а бэкенд отклоняет имена со слэшами.

Раскладка с версией в пути (`arbitr/models/v0.3/...`) приложению не видна — она пригодится
только если приложение когда-нибудь начнёт читать `manifest.json` напрямую из хранилища.

## Проверка после заливки

Через тот же путь, которым ходит приложение:

```bash
curl -sI -H "Authorization: Bearer <ключ>" \
    https://<хост бэкенда>/download/qwen3.5-2b-q4_k_m.gguf
```

Ожидается `200 OK` и `Content-Length`, равный размеру из манифеста. `404` — файл лежит не по
тому ключу.

## Что внутри

```
manifest.json                              читается первым, ~2 КБ
qwen3.5-2b/qwen3.5-2b-q4_k_m.gguf          1222 МБ — iOS / Android
qwen3.5-0.8b/qwen3.5-0.8b-q4_k_m.gguf       508 МБ — Аврора
shared/rubert-tiny2.onnx + токенизатор      114 МБ — нужны при любом выборе
resources/prompts/ + resources/grammar/      24 КБ — промпты и грамматики
```

Пользователь качает **один** вариант модели плюс `shared` и `resources`:
1.30 ГБ для полной модели, 0.61 ГБ для лёгкой.

## Чем отличается от v0.2

**Веса те же самые**, байт в байт. Новое — три вещи:

1. **Промпт `resources/prompts/score_level_hints.txt`** — по нему теперь оцениваются критерии
   с подкритериями. Без него приложение не сможет воспроизвести текущую схему оценивания.
2. **Требования к железу в `manifest.json`** — у каждого варианта появились `min_free_ram_mb`,
   `recommended_free_ram_mb`, `min_cpu_cores`. Приложение должно выбирать самый тяжёлый вариант,
   который устройство проходит по **свободной** памяти (`MemAvailable`), а не по названию
   операционной системы. Если не проходит ни один — показать сообщение, а не качать гигабайт,
   который потом не загрузится.
3. **Версия в пути** — `v0.3`.

## Важно: одной заливки мало

Промпты приложение читает **из своей сборки** (`assets/model/`, через `rootBundle`), а не из
скачанного каталога. Новый промпт доедет до пользователей только с релизом приложения — либо
после того, как приложение научится брать `resources/` из скачанного каталога.

И главное: основные улучшения качества — это **код**, а не файлы. Сейчас в приложении критерий
без подкритериев получает 0 баллов, не обращаясь к модели вообще. Что именно нужно поменять,
расписано с готовыми кусками кода в `~/Desktop/arbitrator_mobile_scoring.md`.
